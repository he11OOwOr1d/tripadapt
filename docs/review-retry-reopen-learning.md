# Reopen an interrupted draft review

17 November follow-up: a new automated scenario composes the real submission adapter and retry-storage helper with a simulated server receipt store. The simulated server saves a pending review, then loses its response. Reopening with a newly generated fallback key reuses the stored original key and retrieves the single original pending review. The test also checks matching-key cleanup. All 183 frontend tests pass. This closes the client-side regression gap for a post-save lost response; it is not a live backend or browser reproduction of that failure. No production code changed in this follow-up.

16 November 2026. A traveler could retry a draft review with the same request key while its dialog remained open, but reloading the tab generated a new key. If the server had saved a review before the response was lost, that could produce another review for the same draft.

The pending submission key is now kept in tab session storage before the request, scoped to the trip and exact saved-draft version and limited to 24 hours. Reopening that same draft reuses the key; the backend's existing idempotency boundary returns the original review if it had already been saved. A received response clears only its matching key. Changing trip or draft uses a new key, and sign-out or starting a new trip clears the stored pointer. It contains no itinerary content, location, token or credentials. If browser storage is unavailable, same-dialog retries still work, while recovery after a reload is not guaranteed. A reopened original review can be stale if the accepted plan changed; existing review guards still determine whether it can be accepted.

During browser verification the full review also showed a missed activity without its outcome label. The review now labels it “didn’t happen,” retaining the saved record and its timing without implying it was completed.

Verification: 182 frontend tests passed, including same-draft reuse, trip/version isolation, expiry, malformed/unavailable storage and clearing only the matching key. TypeScript and production build passed. In the signed-in browser, the local backend was briefly stopped during review preparation. After restarting and reloading, reopening the review succeeded; the missed activity was labeled correctly. The test review was discarded, no plan was accepted, and the QA draft matched its baseline when activities were compared by ID. The browser test interrupted the request before a server commit; it did not reproduce a response lost after a successful commit. Reuse across reload is checked by the storage unit tests and relies on the backend's existing idempotency behavior. No finalized product documents, deployment or real bookings changed.
