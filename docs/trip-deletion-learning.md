# Deleting a trip: learning note

21 November 2026. PRD FR-11 says a traveler can reopen **and delete** trips, and the API design lists `DELETE /trips/{trip_id}` (202: hide the trip, disable monitoring, cancel jobs, schedule a purge). The database already had `trip.deleted_at`, and every read already ignored deleted trips, but there was no way to delete. The status notes said so ("the app has no delete or rename"), and my own QA trips could not be cleaned up.

## What it does

- **`DELETE /api/v1/trips/{id}`** needs the trip's current `If-Match` version (428 without it, 412 if the trip changed since it was read), as `PATCH` does. In one transaction it stops the trip's unfinished planning jobs, sets `deleted_at` and bumps the version. It answers 202 with the id and the time.
- **Stopping jobs** is one shared function (`app/jobs/cancel.py`), also used by the existing "cancel job" endpoint: a queued job is cancelled outright and can never be claimed; a running one is told to stop; finished ones are left alone. A job row the worker holds locked at that instant is skipped rather than waited for, because the worker takes the job lock then the trip lock and delete takes them the other way round; skipping is safe because the worker re-reads the trip before publishing and already treats a deleted trip as superseded.
- **My trips** now has a **Delete** button per trip with an inline confirmation: "It is hidden from your account now and permanently erased after 30 days. Any planning in progress stops. This can't be undone from the app." After deleting, the notice gives the real date ("…will be permanently erased on 21 Dec 2026"), taken from the server's answer. The safe choice ("Keep it") has the focus, backing out returns focus to that trip's Delete button, and after a delete focus moves to "Start a new trip" and a polite notice says what was deleted. Failures are said plainly ("Nothing was changed; try again in a moment") and the trip stays listed.
- **Deleting the trip that is open** lets any in-flight save finish first (so it cannot land after the delete), then returns to a blank new trip with the library still open, and overwrites the device copy of that trip so its content does not linger in this browser.
- **A trip already deleted elsewhere** (a stale list, another tab) counts as deleted: the traveler asked for it to be gone, so a 404 is not an error. If the trip changed between reading its version and deleting (its own autosave, another tab) the version is read again and the delete retried, up to three times.

## Permanent erasure after 30 days

The owner chose a **30 day recovery window, then true erasure** (21 November 2026). Until then a deleted trip is only hidden; its rows can be restored by a database administrator by clearing `deleted_at` (there is no in-app undo). After the window, `app/jobs/purge.py` removes everything the trip owns.

- **Settings:** `TRIP_RETENTION_DAYS` (default 30, never less than 1, so a typo can never mean "now"), `TRIP_PURGE_ENABLED` (default on), `TRIP_PURGE_INTERVAL_MINUTES` (360) and `TRIP_PURGE_BATCH` (25 trips a run).
- **Where it runs:** inside the existing background worker on the web service, two minutes after start and then every six hours, so there is no paid scheduler. It therefore runs only while the web service is awake and its embedded worker is on (on Render's free tier the service sleeps when idle, so a trip may be erased somewhat later than 30 days, never earlier). By hand: `python -m app.jobs.purge` is a dry run that changes nothing; add `--execute` to erase.
- **What is erased:** conversation turns, planning jobs, proposals, creation receipts, every plan version (and so its stops, activities and costs, by cascade), then the trip. **Not** erased: shared place snapshots and users, which belong to no single trip. Database backups kept by the hosting provider are outside this app's control.
- **Safeguards.** A trip is erased only if it is marked deleted *and* was deleted more than the window ago, checked twice (when listing, and again under a row lock). A trip that was never deleted can never be erased, however old. Each trip is its own transaction, so a failure leaves that trip whole and the rest still go; a failed trip is tried again next run. The log and the report carry ids and row counts only, never titles or content, and a failure logs the kind of error only.
- **A new migration (0027) and why.** The database refuses, by trigger, any change or deletion of an accepted plan version or of the stops, activities and costs under it. That protection stays for everything else, but erasure has to delete them. The migration gives the guard one narrow exception: a **delete** is allowed only in a transaction that has declared, with a transaction-local setting, that it is erasing that exact trip. Updates, deletes for any other trip, and anything without the declaration are refused exactly as before. The purge sets the declaration for one trip, deletes, and clears it. The migration test proves this three ways and also that downgrading restores the old strictness.
- **Self-check.** One test reads the live schema and fails if any table points at a trip (directly or through a version, proposal or job) that the erase list does not cover, so a future table cannot silently keep a deleted trip's data.

### Deploying this: order matters

1. Apply migration 0027 to the hosted database (`make migrate-supabase`) **before** the new backend runs. Without it, erasing a trip that has an accepted plan fails safely (rolled back, logged, retried), so nothing is lost, but nothing is erased either.
2. Then push; Render restarts and the first cleanup runs a couple of minutes later. Nothing is due at first (no trip has been deleted for 30 days), so the first run changes nothing.

## Bugs found on the way

- **CORS refused the request.** The API allowed only `GET`, `POST` and `PATCH` from the web app, so the browser's preflight for `DELETE` was answered 400 and the first live delete failed (gracefully, with the right message). The 654 backend tests passed because the test client does not enforce CORS. It is fixed, with a test that checks the preflight directly (allowed for the web app's origin, refused for another origin and for `PUT`). On the hosted site this would have broken deletion after deploy.
- **Focus was lost** after "Keep it" (it fell to the page body); fixed by returning it to the Delete button. Found by checking, not by a test.

## Checks

- Backend (deletion): 11 new tests, 655 pass. They cover the version requirement, hiding from reads and the list, other trips untouched, deleting twice, another traveler, queued jobs, a running job that never publishes, finished jobs left alone, and a **walk over every route in the API that takes a trip id**: after deletion none may succeed (GETs must answer 404; anything else must be a 4xx). I broke the code three ways on purpose (reads forgetting `deleted_at`, jobs not stopped, delete skipping the job step) and each was caught.
- Frontend: 6 tests for the read-version-then-delete logic (already gone, version changed and retry, bounded retries, other errors not retried, a missing version never guessed); 311 pass.
- Live (local app, local API, the real account database, disposable "QA delete test" trips only; the two earlier QA trips were not touched): confirmation shows with focus on "Keep it"; Keep it returns focus; delete removes the row with a notice; the API then answers 404 and the list omits it; deleting the open trip with an unsaved edit in flight resets to a blank trip, keeps the library open, shows no sync error, overwrites the device copy and does **not** create a new trip afterwards; a trip deleted elsewhere is handled without an error; with the API stopped the app says it could not delete and keeps the trip, and a retry after the API returned deleted it. All four disposable trips were deleted with the feature itself.
- The dialog markup was also rendered in a guest page (the signed-in window cannot take screenshots) at 1280 and 390 px: no controls under 44 px, no overflow.
- **Not checked:** the hosted site (not deployed), a screen reader, and the unverified assumption that a deleted trip's worker-side leftovers (a conversation reply already saved for it) are harmless because nothing can read them.

### Checks for the erasure (21 November 2026)

- **Backend:** 16 more tests (671 pass in all). A trip is built with something in **every** table that belongs to a trip (a test first proves that), deleted, aged past the window and erased: zero rows remain anywhere. The window is exact to the second (29 days kept, exactly 30 days kept, 30 days and one second erased). A never-deleted trip is never touched however old; other trips (same owner or not) are untouched and still served; shared place snapshots and users survive; a dry run changes nothing; the batch limit holds and the rest wait; a failure part way through rolls that trip back completely, the others still go, and it succeeds on the next run; a window under a day is refused; the worker's timer runs once per interval and a failure does not stop it.
- **Attacks on my own code.** I broke each safeguard on purpose. Dropping the "is deleted" check was caught only when both independent checks were dropped (either alone is harmless, by design); an off-by-one on the boundary, a missing declaration to the database, forgotten child tables and a zero-day window were each caught. The migration test was likewise caught when the declaration check was loosened.
- **First real run found a real problem.** The first erasure failed against PostgreSQL with "Accepted version is immutable": the protective trigger above. A hand-written mock would not have found it; it is why migration 0027 exists.
- **On the real database** (the hosted database, with my own four disposable "QA delete test" trips, aged past the window with one checked statement): a dry run found exactly those four; the erasure removed 16 rows; they are gone from all nine tables; the other 10 trips (including other accounts' trips, none of them deleted) are unchanged row for row; a second dry run finds nothing. This confirms the database role has the privileges it needs. Those trips were drafts, so this did **not** exercise accepted-plan erasure on the hosted database: that is covered by the throwaway-PostgreSQL tests using the real migrations, and is the first thing to watch after deploying.
- **Not checked:** the hosted site after deploy; behaviour when the web service sleeps through a window; an erasure while the owner is using that trip in another tab (it would simply be hidden already).
