# Conversation to the weather replacement chooser

14 November 2026

## What changed

Chat recognizes requests for a museum/gallery alternative to a named flexible activity on the selected day. Groq routes the intent and extracts a bounded activity ID, category preference and optional explicit ISO date. The server validates that activity and returns a read-only chooser action. It does not select a venue, retrieve a forecast, create a proposal or edit the itinerary through that reply.

The action opens the existing weather panel, focuses it and carries the activity, category preference and date. The traveler checks the forecast, chooses a retrieved place and opens the same typed weather-change proposal used by the form. Existing acceptance, freshness, protection and optional Google checks remain authoritative. Chat cannot bypass them.

## Decisions and trade-offs

- **One edit boundary.** This slice connects conversation to the proven chooser instead of building another model-driven replacement writer. It deliberately does not complete venue selection entirely inside chat. More automatic conversational discovery is still a follow-up.
- **Separate routing from facts.** Two bounded structured-output calls identify intent and an existing activity. No weather or place facts are generated by the model. The existing Python/Groq worker stack remains in use; no framework migration or new API key is needed.
- **Keep identity and scope explicit.** Unknown activities, a different selected day/destination, duplicate names, protected/completed/booked items and missing destination references ask for clarification rather than opening a guessed target. Duplicate names currently need distinct labels in Plan even when other clues might disambiguate them.
- **No silent dates.** An extracted check date must be a valid YYYY-MM-DD copied from the current message. Otherwise the chooser requires a date, or uses the exact saved schedule date. An explicit conflicting date on an exact trip produces clarification. Relative and prose dates are not resolved by this slice. Flexible check dates do not become trip dates.
- **Persist an action, not an edit.** The worker stores typed action metadata with the conversation job after its normal lease/cancellation/fresh-base checks. It binds the action to the draft ETag and selected activity/day. The owner-scoped messages response revalidates it against the current draft and marks old actions stale. Client checks additionally prevent launching another trip/day, an outdated version or a now-protected/missing activity.
- **Recover without overwriting work.** Reload can recover the action from the stored conversation. Opening it preserves an unsent composer message. The date/forecast chooser starts fresh instead of reusing old provider results. Explicit day/destination navigation clears the temporary handoff seed; saved trip data is untouched.
