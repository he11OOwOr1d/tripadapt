# Learning: a driving estimate between destinations and from the start

20 November 2026. The arrival and departure cards in the day view said "Transport to decide" and nothing more, which left the biggest travel question of a multi-destination trip unaddressed. Each card between two mapped destinations now has an **Estimate the drive from X to Y** button that shows, for example, "About 3 h 23 min by road, 269 km" (Jaipur to Agra, live). It is a single, explicit lookup that changes nothing.

## What it is and is not

It is a **driving estimate between the two destination centres**, from the same Geoapify routing used by the other journey checks, without live traffic. It is **not** a train, bus or flight schedule, a mode recommendation, a fare, or a booking. The card says so, shows the Geoapify and OpenStreetMap credit and the time it was checked, and does not touch the traveler's own "travel time" entry on its own; see the next section for the optional button.

## Decisions and tradeoffs

- **Retained references, not coordinates from the browser.** `POST /api/v1/journeys/intercity` takes two destination reference ids and reads the coordinates server-side from the retained place records, so the request cannot be used to route arbitrary points. It rejects the same place twice (422), unknown ids (404) and unknown fields or modes (422, the mode is fixed to drive), needs sign-in (401), returns `Cache-Control: private, no-store`, reuses the per-user route rate limit and writes nothing. A provider failure is returned as an error, never as zero minutes.
- **Mapped ends only.** A button appears only when both ends are mapped. A destination is mapped when it has a retained location reference. The trip's starting point used to be only a name, so the first and last journeys had no button; see the starting-point section below.
- **Drive only.** Free route data has no timetables. Walking between cities is not meaningful, so the mode is not offered.
- **No total, no side effects.** The result lives in the component and is discarded when either destination or its map link changes (the card is keyed on both).

## The starting point, later the same day

The first journey (start to the first destination) and the finish journey (last destination back to the start, when "return to my starting location" is on) were the likeliest ones a traveler wants a time for, and they had no button because the starting location was a plain text field. It now uses the same map search as destinations ("Starting location", with "Search places"). Choosing a match stores the name and a map point; **typing in the field clears the point**, so a name the traveler typed is never matched to coordinates it did not come from, and a typed-only start behaves exactly as before.

- **Where the point lives.** The backend already allowed optional latitude and longitude on the trip origin (`Location`), so no schema, migration or finalized design document changed. The frontend keeps `originPoint` (latitude and longitude) beside the origin name, sends it with the origin, and reads it back; the server returns decimals as strings, which a small pure function (`originPointFrom`) turns into numbers and rejects when missing, partial, out of range, or 0, 0.
- **Endpoint change.** `POST /journeys/intercity` now takes `origin` and `destination`, each either a retained `reference_id` or a pair of coordinates (never both, never one coordinate, never 0, 0). Coordinates are accepted because the starting point is not a retained reference. They are the traveler's own saved start; the endpoint is rate limited and signed-in like the others, and the same-place check also compares resolved coordinates.
- **Finish legs.** Only "return to my starting location" is covered. A separately typed finish location is still only a name.
- **Compatibility.** An older backend and frontend ignore or already accept the optional origin coordinates, so this adds no rollback hazard beyond the endpoint itself (it simply would not exist on an older backend).

## Using the estimate as the traveler's own travel time

After a result, an explicit button offers **Use 3.12 hours as my travel time** (or **Replace my 5 hours with 3.12 hours** when an entry exists). Pressing it writes the hours into that journey's existing "Approximate hours" entry, the one the traveler can also type in the trip form, so the plan and the day card agree and the card then says "Your own travel time already says 3.12 hours". It never happens automatically, it changes only that one journey's hours and no other field (the mode, nights on the move and allowance stay), and the traveler can edit or clear it in the form. Hours are rounded **up** to the next hundredth (187 min becomes 3.12), because the server accepts at most two decimals and a trip planned on a slightly longer time is the safe side. It is disabled while an editor is open, like the other plan-changing buttons.

- **Verification:** 2 new frontend tests (rounding including 0 and negative input, and the pure update that adds, replaces and leaves other journeys and fields alone; 219 frontend tests pass); typecheck and build pass. Live, signed in, on the QA trip with its starting point set from the map search: the arrival card read "Transport to decide", the estimate gave 3 h 7 min, **Use 3.12 hours as my travel time** changed the card to "Transport to decide · about 3.12 hours", the card then showed "Your own travel time already says 3.12 hours", and the trip form's hours field held 3.12 after the change. Axe found no violations. I cleared the hours in the form and put the starting location back to plain "Delhi"; after a reload the card was back to "Transport to decide" with no estimate button and the session was still signed in.
- **Restore caveat:** the app cannot delete a journey's preference entry once it exists, so clearing the hours leaves an all-default entry (empty mode and hours, 0 nights, no allowance) in place of no entry. Every calculation treats the two the same; only the restore review's wording differs ("mode open; unknown hours; ..." instead of "preferences left open"). This is a small deviation from restoring the QA trip's exact original data.
- **Not verified:** the hosted app, a screenshot, and replacing an existing non-empty entry live (covered by the pure update and the button label logic, not clicked).

## Road time across the whole route

"See the whole trip" now ends with a **Road time across your route** panel: the route's journeys in order (start, each destination, and back to the start when the trip returns), each with its estimate, and one button, "Estimate all 4 mapped journeys", that looks them up one after another. When every journey has a result it says "About 20 h 39 min of driving, 2033 km across 4 journeys"; with some missing it says "... across the 1 of 3 journeys estimated so far", so a partial sum is never presented as the trip's total. A journey with an unmapped end says "Needs a map location at both ends" and is not counted; a typed finish location is never mapped. A failure on one journey is shown on that journey and the others continue. It is explicit (nothing runs on opening), sequential (one request at a time, within the per-user limit), cancelled when the route changes or the page is left, writes nothing, and the same caveats apply (centre to centre, no traffic, no breaks, not a timetable).

- **Logic:** pure functions (`routeJourneys`, `driveSummary`, `driveSummaryLine`) pair the existing route legs with their map ends, so the panel and the per-day cards agree. 4 new frontend tests cover the pairing with and without return, a typed finish, estimability, and totals for none, some and all journeys (223 frontend tests pass); typecheck and build pass.
- **Live, signed in, on the disposable three-destination QA trip** (Delhi start; Jaipur, Agra, Varanasi): the panel listed Delhi to Jaipur, Jaipur to Agra, Agra to Varanasi and Varanasi to Delhi, and "Estimate all 4 mapped journeys" returned 3 h 7 min / 304 km, 3 h 23 min / 269 km, 6 h 18 min / 634 km and 7 h 51 min / 826 km, totalled as **20 h 39 min, 2033 km**, which matches the sum of the four. Axe (WCAG 2.0 to 2.2 plus best-practice) on the page found nothing from the new panel; it found 9 contrast failures in the existing whole-trip overview text that had not been audited before (a muted green at 3.85:1), now darkened to #5d6e4f like the others, after which axe is clean. At 390 px there was no overflow and no control under 44 px. The main QA trip was not touched.

## Review follow-up (20 November 2026)

A code review of the intercity commits found these, now fixed:

- **A rounding bug in "Use X hours".** The hours were computed as `ceil(minutes / 60 * 100) / 100`, and floating-point error turns exact values such as 33 minutes (0.55 hours, but 55.00000000000001 in floating point) into 0.56, so the traveler's own field could be one hundredth too high. It now scales to integers first, and a test checks every whole minute from 0 to 3000 against exact integer arithmetic, plus 33 and 66 minutes explicitly. Before this fix about 70 of the first 3000 values were wrong.
- **A malformed retained reference caused a 500.** A reference without usable coordinates (missing, null, non-numeric, out of range) is now a handled 422 with the stable code `PLACE_LOCATION_UNAVAILABLE`, for either end, with six parametrized tests. (Postgres cannot store infinity, so that case cannot occur in the table.)
- **The button was offered for a journey from a place to itself.** A starting point chosen from the map and a destination at the same coordinates (a trip that starts in Kyoto and visits Kyoto), or two references within about 100 m, took different forms, so the client could not tell and the server answered 422. The destination and the start now also carry their own coordinates for this comparison, and no button is offered for such a pair.
- **The starting-location field reused destination wording and trapped Enter.** The search status and list label now say "places" for the starting location and still say "destinations" for destinations, and Enter in the starting-location field keeps its usual job instead of starting a search (the search button and its keyboard access are unchanged). The destination field still searches on Enter.
- **An unused import** was removed.

Verified by tests only, not re-run in the browser: 225 frontend and 592 backend tests pass (the new ones included), typecheck, ruff and the build pass, and the OpenAPI snapshot is unchanged. The live behavior that matters here (the estimate itself, the cards and the whole-route panel) was verified earlier and the changes do not alter their requests.

## Quota, a cache, and a security review (20 November 2026, later)

I ran a manual security review of the new endpoints (the skill's own diff command needs an `origin/HEAD` this checkout lacks, so I read the code instead). Findings and decisions:

- **Authentication and validation hold.** All of `/journeys/from-stay`, `/to-stay` and `/intercity` need sign-in (tests assert 401); inputs are strictly typed with finite, range-checked coordinates; provider URLs are fixed and parameters are URL-encoded, so there is no request forgery path; responses are `private, no-store`; no endpoint writes data. The place and reference ids are public provider data, so looking them up by id is not an access-control gap (the same as the existing hours and journey checks).
- **Quota was the real exposure.** The provider limiter is shared: 40 requests a minute for the whole process, 300 a day per user, 1000 a day overall. The whole-route panel can spend one request per journey per click, and a busy minute from one trip would crowd out others. The intercity endpoint now has a small in-process cache (up to 512 entries, six hours, least recently used out first), keyed by the two coordinates rounded to about 10 m, direction included (the return road can differ). It stores the original retrieval time, so a cached answer is never shown as fresher than it is; failures are never cached; the value is a public road route, so sharing it across users leaks nothing. Tests cover a repeat costing no provider call and returning identical data, the reverse and a different pair costing one each, failures not cached, expiry and the size bound (595 backend tests pass). The cache is per process and is lost on restart; it is a cost guard, not a durability feature.
- **Privacy disclosure added.** The stay and starting-point coordinates leave the app for the route provider. That is the traveler's own explicit action and the credit already named Geoapify, but the text now says so where each result appears: "the map point of your stay and of the visit is sent to the route provider, Geoapify", and the same for the two places in the intercity estimate and the whole-route panel.
- **The AI paths.** The stay name and address reach the language model only as untrusted text with no coordinates, the model can add only supplied catalog ids, and the checks after it are unchanged, so a hostile name cannot add an arbitrary place or booking. Nothing from the route endpoints reaches the model.
- **Left alone:** the per-process limits are in memory, so a multi-process deployment multiplies them; moving them to the database is a separate task. Frontend text is rendered by React (escaped), and no new link or `dangerouslySetInnerHTML` was added.

Live check of the cache and the disclosure (disposable trip, signed in): pressing the same estimate twice showed "Checked 11/20/2026, 1:44:03 AM" both times, so the second answer came from the cache with its original time, and the disclosure sentence appears under the result. Not verified: expiry in a real process (covered by the unit test with a fake clock), or behavior across two server processes.
